# Canonical page copy

Status: current-source preparation, typed reference remapping, the 2416 file
provenance schema and an atomic canonical copy service are implemented and
tested for the implemented source shapes. The principal synced-reference copy
rules were verified directly in Notion on 2026-09-16. Explicit synced originals
and references now have a current-authority GET, passive rich-text reference
display, flat creation UI and copy remapping; see `synced_block_contract.md`.
Canonical copy transport, durable recovery UI and real-browser flat text/synced
group copying are connected. Legacy origin adoption, reference-location shared
editing, nested reference display, live source subscriptions and complete
linked/synced shape coverage remain unfinished.
The duplicate HTTP route now distinguishes ordinary and collaborative storage;
collaborative requests cannot fall through to the legacy writer. Its canonical
branch and receipt lookup are staged behind an explicitly false server capability.
No public copy capability is enabled yet.

## Required resulting behavior

Copy the current authorized page and its active descendants into independent
canonical documents, preserving visible rich text, nested blocks, page appearance,
database properties/rows/cells/views/templates and attachments. Internal page,
block, database, row/property and file references must target the corresponding
copies. External references remain external and never grant new access. Ordinary
user text that happens to equal an ID must not be rewritten. Shares, sessions,
comments, pending uploads, history and deleted descendants are not duplicated as
new grants or as editable user content. Synced-block reference boundaries follow
the direct comparison below. Partial-restore link behavior still requires explicit
Notion comparison; do not guess its parity.

Only current workspace owners copying their own page subtree are covered by the
existing lifecycle authorization contract. Current source readability and current
destination edit/lock checks must be repeated at commit. Source locks alone do
not justify modifying the source. The existing 128-document operation bound is
retained and source preparation has an explicit 64 MiB metadata/replay budget;
exceeding either must fail without exposing a partial copy.

## Preparation and commit boundary

`page_copy_source.prepare_page_copy` collects one SQLite read snapshot, including
the current CRDT generation/frames and canonical database/file descriptors. It
replays durable Yjs updates and checks attachment bytes outside all database
transactions. It then rechecks hierarchy, workspace/document epochs, row versions,
generations and the destination parent. The returned immutable source object is
not an authorization lease. `revalidate_copy_source` must run again inside the
copy transaction immediately before any inserts.

`page_copy_remap.remap_page_copy` now returns an immutable `PageCopyPlan` retaining
the original preparation witness. Descendant, property, row and view positions
are normalized in source order so tied old positions cannot reorder new IDs.
The root retains its source position in the plan; the writer derives its actual
insertion position from current destination siblings inside the transaction.
Template IDs include an ordinal prefix because their existing canonical reader
orders equal creation timestamps by ID. This preserves visible template order
without inventing timestamps or changing historical table definitions.

The remapper allocates deterministic IDs per actor/workspace/operation and typed
source scope. It transforms page/child links, block anchors in rich HTML links,
column groups, tab controllers/tabs, nested blocks, owned canonical databases,
properties, rows, relation cells, rollups, formula reference bindings, view
filters/sorts/visibility, template bodies/defaults and active file records.
Ordinary text, display labels, people IDs and external reference targets remain
unchanged. Archived views/templates are not revived. DB versions start at one;
computed values and stale block-level DB caches are regenerated by the existing
canonical hydration path, using the copied current database descriptors.

Rich HTML transformation edits only URL attribute values, retaining markup and
text outside those values. Absolute links are remapped only when the eventual
caller supplies a trusted configured application origin; relative page/file
routes can be remapped without one. This is not permission to trust arbitrary
client-origin claims. Root-site and file fragments are not treated as page block
anchors. File plans contain independent IDs and explicit source file/document
provenance with verified blob metadata, and never contain fabricated/reused upload
sessions. Their eventual insertion requires the exact 2416 schema; older
upload-only file schemas cannot represent these plans.
Page appearance's `nf:` image-icon binding is remapped at that typed field, so
it uses the destination file's authorization after the source file is deleted.

Formula expressions and string-valued cells remain unchanged. A validated
`config.copy_property_ids` map is applied only at the formula evaluator's `prop()`
resolution boundary, including dynamically constructed IDs and nested `prop()`
calls. It resolves through the existing current-database row resolver after
relation access filtering; it cannot read another database or create access.
Copying a copy flattens previous bindings onto the new property IDs. The frontend
canonical bridge retains this map during hydration and later schema edits.
Expanded plans have a 64 MiB output budget, and formula-binding accumulation is
checked before final serialization to bound growth across many formulas.

Legacy sync_id-only blocks and linked/unadopted databases currently raise
`CopyShapeUnavailable`. Their full-fidelity behavior is still required before
capability/API/UI activation; this rejection is a development boundary, not the
intended finished feature. The synced-block rules below are observed; explicit
origin/reference descriptors, current read checks and copy remapping are now
implemented. Rendering, shared editing, legacy adoption and template-origin
instantiation remain unfinished. External two-way relation behavior and partially restored child
links still require the documented Notion comparison. No copy capability is
enabled by this stage.

access to both documents, and rejects a change or revocation during preparation.
The combined read/replay budget is 64 MiB. The result retains the original
document identity and file links; it neither grants access nor writes a receipt,
cache, revision, event or legacy row.

## Atomic service and recovery

`page_copy.copy_page` inserts independent documents, blocks, DB data, active file
records, native-copy registrations, initial revisions/generations/checkpoints,
parent links, receipts, audit and outbox in one service transaction. Every copied
document gets an event at its initial sequence. The parent receives the existing
typed-command and durable-Yjs link records. Node replay, file hashing, expanded
payload validation and disk headroom checks happen before entering the writer.
The writer rechecks current actor/workspace authority, every source stamp, the
parent stamp and the exact source file metadata before insertion. The inserted
canonical descriptor must equal the prepared content.

An exact replay reauthorizes current workspace ownership and ownership of all
resulting documents. It does not depend on the source still being active or
readable. `read_page_copy_result` is read-only and distinguishes an absent receipt
from a committed result, including whether the resulting root is now archived.
Changed input with the same operation ID fails. A competing identical operation
can be recovered both during preparation and at the final transaction boundary.
The service changes the workspace navigation version and existing search
invalidation counter, without changing source rows or creating new grants.

History restore retains the exact string stored in a revision, including an empty
title and intentional leading/trailing spaces. It rejects a missing/non-string
title or one exceeding the existing 1,000-character bound. It does not substitute
a display placeholder into canonical content. Actual copy -> later edit ->
restore -> reopen -> idempotent replay tests cover empty title/body and a spaced
Korean title. These two regressions and the existing source/history suites passed
11 tests on 2026-09-16 (`115.16s`).

## Staged HTTP transport (2026-09-16)

`POST /api/notion/workspaces/<workspace>/pages/<page>/duplicate` dispatches to
canonical copy only in collaborative mode and only when the server-owned
`collaborative_page_copy` capability is true. The current runtime always returns
false, including at schema 2416; the disposable HTTP tests alone override it.
Ordinary mode retains its original `base_version` contract. The canonical body
contains exactly `operation_id`, `expected_document_sequence`,
`expected_workspace_epoch` and `expected_document_epoch`.

`POST` to the same path plus `-result` accepts the identical original request.
It returns `unknown` without writing anything, or the committed result and the
destination's current archive state. Recovery authorizes current ownership and
the result documents, so archiving the source does not hide a successful copy.
The same operation with different input remains a conflict. Responses use
`no-store`; source changes return 409 and unsupported copy shapes return 422
without exposing preparation details or creating a partial copy.

Absolute internal links may be remapped only using the host-configured
`NOTION_CANONICAL_ORIGIN`. Its default is empty, retaining the existing
relative-link-only behavior. Request JSON, Host and Origin headers cannot set
this trusted copy origin. Deployment must keep it stable during pending operation
recovery because it is part of the existing copy request digest.

The collaborative frontend accepts the explicit server copy capability for its
menu and function entry points. The runtime still returns false, so the action
remains hidden and never falls back to the legacy writer. This is an explicit
temporary availability boundary, not completed Notion copy parity.

## Staged frontend recovery (2026-09-16)

`notion_page_copy.js` stores the original operation and three expected stamps in
localStorage, scoped by user, workspace and source page. It verifies storage
before POST and refuses to start if storage is denied, malformed or silently
fails. It never stores editor content, access grants, or an authoritative copy
of server metadata. Duplicate activation within one controller shares a flight;
independent tabs and frames coordinate through an exclusive Web Lock.

After reload or an uncertain response, lookup of the original receipt precedes
editor flush, metadata reads or mutation. A committed receipt therefore remains
recoverable when the source is archived or its editor is blocked. An unknown
receipt can be checked without mutation or explicitly retried using the exact
original operation and stamps; it does not mean no older request is in flight.
A definitive rejection before server intent registration permits a corrected
explicit attempt. Once the server has registered the request, a copy rejection
still leaves that intent pending: the original request remains visible for result
lookup, exact retry or explicit cancellation. A later rejection after uncertainty
also retains it. The confirmation control cannot discard an unresolved request.

The UI holds both editor surfaces while flushing before a new copy or retry,
refuses IME composition, and checks account/workspace/navigation/open-editor
identity across awaits. Receipt recovery refreshes navigation with
`preserveActivePage: true`; it does not replace dirty main or side-peek content.
A late response is retained under its original scope without changing the new
screen. Confirmed results remain discoverable until explicitly acknowledged.
Opening a copy first rechecks its receipt and current archive state and then
uses the normal guarded page-opening path. A failed list refresh cannot create
another copy. Pending or uncertain requests participate in beforeunload protection.

Initial recovery-packet evidence: 19 new Node cases exercise the controller and extracted real UI/input
hold functions. Twelve Node scripts passed together (41 runner results, with
some legacy scripts grouping scenarios internally), and the existing five HTTP
copy tests passed. Chrome verified final assets, unchanged body/menu behavior,

### Shared intent coordination (2026-09-16 follow-up)

Every record mutation, including acknowledgement and adoption of a previous
tab-local intent, runs under the same source-scoped exclusive Web Lock. The
non-waiting `ifAvailable` path returns busy when another context holds it; it
never steals the lock or falls back to uncoordinated writes. Unsupported or
denied lock/storage access refuses mutation. The browser lock is not a server
authorization boundary and does not replace canonical idempotency or CAS.

Acknowledgement and first definitive rejection retain one terminal marker per
source. The operation observed when a click begins is compared with the record
under lock, so a click delayed across another tab's acknowledgement cannot
accidentally become a new copy. A subsequent explicit activation can start a
new operation. Recovery-panel actions bind their operation ID; stale controls
cannot act on the next operation for that source.

Storage events trigger a fresh read of the shared store, not application of the
event's payload. UI rendering remains account/workspace scoped and leaves both
editors intact. Legacy session records are retired only after their exact request
is verified in shared storage under lock; mismatches preserve both and refuse a
new copy. Normal browser tab closure no longer loses discovery while localStorage
is retained for the same origin and browser storage partition.

The implementation follows the browser's documented exclusive/ifAvailable lock
semantics and cross-document localStorage events.
[Web Locks request](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request),
[storage event](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event).

## Server terminal recovery and cancellation (2026-09-16)

The staged capability now includes POST `duplicate-cancel` with the exact four
fields of the original copy request. It uses the same actor/action/operation key
and request hash as copy. The writer transaction makes either the copy or its
cancellation terminal. Cancellation of a completed copy returns that copy; it
never removes or rewrites it. A cancellation committed first prevents a prepared
copy from inserting documents. The cancelled receipt, event, audit and outbox
commit together, without changing document/body versions or workspace metadata.
Current active workspace ownership is required. Cancelling one's own operation
does not grant access to the source or copy destination.

GET `page-copy-results` discovers only the current actor's terminal operations
within the current owned workspace. Every copied destination is reauthorized,
including archived destinations; revoked ownership hides the complete result.
Keyset pagination uses creation time and operation ID, with actor/workspace bound
cursors. New receipts retain the original immutable request; older receipts can
be discovered without fabricating a request. Routes reject unexpected fields,
use no-store responses, and retain the exact schema/capability gate.

The uncertain-request panel exposes cancellation without flushing either editor.
The workspace menu exposes a result history so a source need not still be visible
and a browser record need not exist. History opens pages through normal guarded
navigation, leaves dirty/composing editors intact, and ignores late responses
after account/workspace/modal changes. Opening history does not replay mutations.

## Durable in-flight copy intent (2026-09-30)

The staged `duplicate-intent` route records the exact actor, workspace, source,
operation ID, request hash and copy stamps through the existing canonical
operation/audit/outbox transaction before the browser sends `duplicate`. It
requires current ownership and source stamps. A second pending operation on the
same source is refused; exact retry returns the original intent. Copy, result
lookup and cancellation reject an operation whose body differs from the recorded
intent. The owner-scoped, paginated `page-copy-intents` route discovers requests
without a terminal copy or cancellation, even if browser storage has been lost.
The recovery panel can adopt the server request under its source Web Lock, check
the result, retry the same operation, or cancel it. It never fabricates a new
operation while recovering the old one.

The staged collaborative `duplicate` HTTP route also requires that registered
intent before a new copy can start. A direct request that skips registration
receives a conflict without writing a copy. A completed receipt from the earlier
pre-intent service remains readable and can still replay; this prevents the new
boundary from hiding an already committed copy. The internal service retains an
explicit opt-out for existing non-HTTP fixture callers, while the browser-facing
route enforces registration.

No schema migration or production feature-flag transition was made. The intent
uses the existing canonical operations table; its distinct action keeps it

## Official Notion references (2026-09-15)

These are documentation observations, not a fresh computer-use comparison.

- Synced content remains connected to its original and requires access to the
  original page. This must not become an independent grant through copying.
  [Synced blocks](https://www.notion.com/help/synced-blocks).
- A linked data source retains its original permissions. Its data edits affect
  the original, while local views, filters and sorting remain separate.
  [Data sources](https://www.notion.com/en-gb/help/data-sources-and-linked-databases).
- Notion documents conversion of a duplicated database's two-way relation to a
  one-way relation rather than adding a reverse relation on the original target.
  [Relations and rollups](https://www.notion.com/en-gb/help/relations-and-rollups).

Consequently, the implementation must distinguish copied owned data from linked
external data. The principal synced-block copy rules were checked by visible
