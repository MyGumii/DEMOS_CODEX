# Historical rich restoration after later input

This additive successor permits a typed identity restoration that predates the
latest current-generation collaborative frame. Later input on another paragraph
must not hide an earlier restoration from native/page/DB/linked-host/row parent
operations or pure page-copy source preparation. Already-applied restoration must
retain newer input and attributed text.

## Complete immutable certificate

The existing bounded generation anchor still requires matching immutable revision
and checkpoint hashes. Complete anchor-to-current replay now accepts an explicit
`restore_deleted` insertion only after an exact deletion of that known identity.
The latest preceding deletion command ID, sequence and target version must match
the restoration binding; the restored version must increment the deleted version
once. A moved/deleted/restored identity still uses its explicit placement anchor.
Unknown identity reuse and restoration without that paired deletion are refused.

Restore binding headers are part of the structural certificate. Exact recovery
ranges are deduplicated with current-tail ranges by immutable command ID and kept
in the internal witness, not duplicated inside its historical certificate.
Restorations are ordered by document sequence so repeated cycles use the latest
recovery while the first tombstone remains immutable. Existing 4096-command,
anchor/history limits and the 8 MiB/256-restoration preparation budget remain.
An over-budget or uncertifiable historical candidate is omitted with its older
restore ranges; the independently bounded current-tail path remains available.
That omission cannot authorize a missing older body from canonical values.

All certificate replay, Yjs replay/cloning and independent projections happen
outside the authorized SQLite reader. Actor, scope, generation, epochs, locks and
exact source stamps are revalidated before the existing atomic domain/delta/
operation-receipt/audit/outbox writer. No original frame, revision, tombstone or
ledger is rewritten.

External linked-host preparation first captures canonical fields, exact row
versions and the witness in the authorized reader, closes it, and only then
certifies history and independently materializes restored content. The existing
whole-workspace linked-reference witness is still rechecked by the final writer;
a linked-host edit after preparation fences the complete domain mutation.

## Latest text versus archived replacement

An absent restored body uses its exact deletion range: archive fields matching
the request retain attributed Y.Text; different explicit values use those values
as plain text. An already-visible body matching the restoration request is kept.
An original-value restoration also keeps later input on its existing map.

For an explicit replacement followed by more input, both validators compare the
current integrated Y.Map creation ID with the deletion archive's state vector.
If its creation clock is at or beyond the archive's next clock for that client,
the map was created after the deletion archive, so its latest body is retained.
The optional pure projection exposes exact visible map IDs and the replayed state
vector only when requested; normal search output is unchanged. A changed older
map whose fields neither match the request nor represent original-value recovery
cannot establish that replacement was applied and is refused before writing.
It is not overwritten with older text.

Independent Python verification compares the complete body/title/order/link
placement plus restored and surviving Y.Text deltas. Attribute-only tampering
is rejected even when ordinary fields stay equal. Pure copy source preparation
returns restored current four-field descriptors without changing source rows;
new copied-generation raw Y.Text attribute fidelity is still separate work.

## Scope and evidence

This packet extends typed restoration inside the certified generation history.
Historical owned-DB restore placement/content, full saves or unexplained domain
histories, nested/archived synced adoption, DB item/template identity and
instantiation, and the original R1–R11 plus C/D/E/F operating review remain.
Normal collaborative schema/flags and normal backend startup are unchanged.

Packet: `20261003-parent-historical-rich-restore`. Exact terminal gates, failed
attempts, qualifications and integration-time source hashes are recorded by the
primary chat integrator in the chat workspace's
`outputs/parent-historical-rich-restore-20261003/phase-evidence.json` when the gate
passes. Earlier current-tail/historical packet evidence stays historical.
