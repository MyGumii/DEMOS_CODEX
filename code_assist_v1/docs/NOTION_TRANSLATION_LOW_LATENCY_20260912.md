# 음성 번역 저지연 설정 및 처리 시간 표시

2026-09-12: 사용자가 한국어→일본어 번역이 약 36초마다 갱신된다고 보고하여,
고정 주기와 수집/전사/번역 대기를 구분하고 저지연 설정을 적용했다.

## 확인한 원인과 한계

- 36초 고정 번역 타이머는 없다. 이전 코드는 녹음 시작 전에 자동 번역을 켜면
  로컬 STT를 4초, 나중에 켜면 이미 시작된 수집을 12초 구간으로 유지했다.
- Computer Use로 사용자 페이지를 읽기만 했다. 해당 노트의 마지막 전사 타임스탬프는
  `[01:24]`, `[01:36]` … `[02:48]`로 실제 12초 구간이었다. 당시 녹음은 종료되었고,
  번역 모델은 `codex-local`, 번역 상태는 서버의 동시 요청 슬롯 점유 안내였다.
  원문 내용 자체는 진단 출력에 포함하지 않았다.
- Codex 번역은 매 요청마다 ephemeral/read-only CLI를 시작하고 전체 JSON 응답을
  검증한 뒤 표시한다. 이전 번역은 자체 reasoning 설정이 없어 CLI 기본 설정을
  상속할 수 있었다. 이 호스트의 config.toml은 astra/xhigh였으나 전역 설정은 변경하지 않았다.
- 정확한 36초의 전사/저장/모델별 분해 측정은 기존 화면에 없었다. 따라서 모두 타이머나
  특정 모델 단계 탓이라고 단정하지 않는다. 새 UI의 전사/번역 왕복 시간으로 구분한다.

## 수정

- 로컬 STT 녹음 구간 기본값 **2초**. 자동 번역 체크 전후 순서와 무관하다.
  `음성 처리 간격`에서 **2/4/8초** 선택, 페이지 저장/재접속 시 유지한다.
  녹음·미전사 구간 처리 중에는 변경하지 않으며 다음 회의 시작 시 적용한다.
  사내/원격 STT의 기존 chunk_seconds는 바꾸지 않는다.
- 자동 번역 debounce **800ms → 100ms**. 자동 요청은 최대 **500자**, 이전 문맥은
  최대 **400자**로 제한해 큰 응답 대기를 줄인다. 수동 원문 일괄 번역은 기존
  2,000자/1,200자 문맥을 유지한다. 이미 처리한 정확한 원문 prefix부터 순서대로
  이어가며 원문 누락/중복이나 무제한 병렬 요청을 허용하지 않는다.
- 번역 전용 Codex 호출 cfg 사본에 `codex_reasoning_effort="low"`를 지정했다.
  선택된 Codex 모델, Gemma4→Qwen3.6→활성/연결된 Codex fallback 순서,
  `--codex` 표시 gate, read-only/ephemeral, 권한 재검증은 유지한다.
  다른 Agent/요약/Second Brain의 모델·추론 설정이나 shared bridge는 변경하지 않는다.
- 화면에 실제 음성 구간 길이, 최근 전사 요청/저장 시간, 미전사 대기 구간,
  현재 번역 응답 대기 시간/최근 왕복 시간/미번역 글자 수를 표시한다.
  이 값은 열린 세션의 진단 값이며 회의 원문/음성을 로그에 기록하지 않는다.
- 전사 요청 시간과 번역 요청 시간은 각각 통신·서버 대기·모델 처리를 포함한다.
  진행 시간 표시는 상태 피드백이지 번역이 완료되었다는 뜻이 아니다.
- 기존 즉시 번역 표시, 저장 실패 시 결과 보존/재시도, 취소·stale 결과 폐기,
  수동 요약 보호와 비우기/편집 권한 계약을 유지한다.

## 실제 Codex 지연 smoke

사용자 음성이나 원문 대신 직접 작성한 짧은 한국어 인사/회의 일정 한 문장을
별도 OS Temp 빈 디렉터리에서 `codex exec --ephemeral --sandbox read-only`, low 설정으로
번역했다. 도구 호출 없이 일본어 JSON을 반환했고 실행 전체 **19.13초**였다.
1회 관측이며 실제 앱의 양방향 JSON prompt, STT/저장 지연을 포함하지 않는다.
사용자 보고 36초와 동일 입력의 통제된 A/B 비교도 아니다.

따라서 2초 수집이 **2초마다 번역 출력**을 보장한다고 주장하지 않는다. 현재 Codex
CLI 실행/응답 지연은 남아 있다. 실제 저지연 통역 SLA에는 별도 측정과 더 빠른
상주 번역 경로 검증이 필요하다. 이 변경은 새로운 STT/LLM 엔진이나 streaming JSON,
음성 합성을 도입하지 않는다. 짧은 구간에서 언어 감지/전사 문맥이 불안정하면 4/8초를
선택할 수 있고, 기존 유한 전사 대기열과 오류 시 음성 보존/재시도 계약도 유지한다.
