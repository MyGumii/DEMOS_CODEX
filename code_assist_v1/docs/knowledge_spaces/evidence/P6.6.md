# P6.6 three-way change-proposal evidence

Date: 2026-08-15 (Asia/Seoul)

## Result

P6.6 passes its isolated three-way proposal service task behind disabled
canonical traffic. Stable-source proposals retain one immutable artifact and
extraction snapshot; personal-to-part proposals retain the fork base and expose
the personal-current and part-current revisions. Preview is read-only. Rebase
creates a new proposal/finding version instead of overwriting drift. Apply
requires the recorded human reviewer and one exact target edit fence before it
creates one target revision.

This is not the aggregate P6 gate. It adds no HTTP route or UI, starts no
worker/model, enables no flag or traffic, and does not claim shadow precision.
P6.7 owns those route/UI/metric surfaces and P6.8 owns aggregate curation
acceptance.

## Fixed preview and authority boundary

- `ProposalRepository.read_snapshot` validates one compatible finding/proposal
  pair, exact row versions and fixed preview hash, immutable revision/body
  hashes and sizes, the current target, and either the stable extraction body or
  the personal lineage/fork/source binding.
- Stable-source preview fixes the extraction snapshot, source/base body, and
  current target. Personal preview renders exactly `fork_base`,
  `source_current`, and `target_current`, plus a separately bound proposed
  result. Personal ownership and current `CURATE` authority are rechecked.
- Inline and blob-backed bodies are materialized outside write transactions.
  After materialization, the complete authorized snapshot is reread and must be
  identical before preview, rebase, or first apply proceeds.
- The fixed preview digest binds proposal kind/version, base/source/target IDs
  and revisions, stable source identities, proposed body SHA-256, finding input
  version, and rule version. Process memory is never an apply authority.

## Rebase and apply closure

- Rebase binds the old proposal/finding versions and exact current source and
  target revisions. It deterministically inserts one next pending pair and
  atomically obsoletes the old pair. Stable rebase cannot replace source
  evidence. Personal rebase may use an explicit reviewed result or capture the
  exact current personal source body.
- Apply requires an approved compatible pair whose `reviewed_by` equals the
  applying actor. It validates expected proposal/finding versions, preview
  digest, current source/target revisions, target row version, held lease token
  HMAC/key, editor session, lease ID, and monotonically increasing fence.
- One transaction queues one `curation.rescan` job, inserts one immutable
  `approved_update` revision/body and `revision_rescan` transition, moves the
  target to provisional, marks finding and proposal applied, invalidates stale
  semantic edges and FTS state, increments space generation, releases the
  lease, and commits audit, outbox, job result, and operation result.
- Apply response-loss replay and rebase replay derive the original request
  binding from immutable SHA evidence and validate the complete terminal pair
  closure before reopening blob storage. Exact replay returns the stored result
  with the new request ID; changed request evidence under the same operation ID
  is rejected.
- Raw lease tokens and authorization metadata are removed from request metadata
  and never appear in audit, outbox, or operation results.

| `PROP-002` | Personal preview fixes fork base, personal current, part current, and proposed result without automatic synchronization. |
| `PROP-003` | Target and personal-source drift make the old preview stale; explicit rebase creates a new version and obsoletes the old pair. |

operation-ID rebinding, incompatible apply-failed review states, stale target
CAS, and confidential request metadata. Nine apply and five rebase failpoints
prove rollback of pair, revision/body, job, lease, generation/search,
audit/outbox, and dedup effects.
