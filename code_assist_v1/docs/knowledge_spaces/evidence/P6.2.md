# P6.2 incremental candidate retrieval evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P6.2 passes its isolated changed-item-only candidate-retrieval task behind
disabled canonical traffic. One current active provisional/published source
revision is rebound to exact canonical body/hash/size/normalizer evidence in one
read snapshot, and at most one same-space FTS5/BM25 query returns a SQL-bounded
top-K of current active/published revisions. The result is body-free and
hash-sealed.

This is not the aggregate P6 gate. No finding, visibility transition, semantic
conclusion, edge, proposal, merge, model call, job, route, feature flag, or
canonical write is created. P6.3 owns persisted versioned findings and policy;
P6.4-P6.8 own review/effect/UI/shadow/aggregate evidence.

## Frozen retrieval boundary

- Rule version is `p6.2-fts-bm25-v1`; retrieval mode is
  `canonical_fts_bm25`; normalizer binding remains `markdown_lf_v1`.
- The public service accepts exactly one `space_id`, source item, source
  revision, exact Markdown body, and `top_k` from 1 through 20. It has no batch,
  corpus-pair, route, worker, network, or model surface.
- Source UTF-8 input is bounded to 2,000,000 bytes. The read transaction
  requires the exact current item/revision/space, active lifecycle,
  provisional-or-published curation state, exact raw/LF-normalized hashes and
  size, and exact inline/body metadata.
- Query generation NFKC-casefolds only Unicode alphanumeric terms, rejects
  overlong term fragments, selects at most 32 deterministic frequency/first-
  occurrence terms, quotes every FTS literal, and seals only the ordered term
  hash/count rather than exposing source text.
- Candidate SQL always contains `knowledge_fts MATCH`, the authorized concrete
  `space_id`, source-item exclusion, current active/published checks,
  deterministic BM25/item-ID ordering, and `LIMIT ?`. Cross-space,
  provisional, inactive, stale-current, and source rows cannot be returned.
- Every returned search title/body is rebound to the immutable revision and
  body metadata. A stale/tampered FTS row fails closed instead of becoming
  evidence.
- Candidate evidence contains IDs, ranks, finite BM25 scores encoded
  canonically, title/content hashes, sizes, and exact/normalized/lexical match
  kind. It contains no Markdown/title text or excerpt.
- `fts_query_count` is exactly zero for an empty token set and one otherwise;
  `all_pairs_scan_count` and `model_call_count` are structurally zero. The
  repository opens no file/network/model surface and executes no SQL mutation.
- The public result validator independently closes UUID/hash/integer shapes,
  source exclusion, item/revision uniqueness, contiguous deterministic ranks,
  finite/order-correct scores, match-kind derivation, top-K/count/version/mode
  invariants, and the canonical evidence hash.

## Gate and residual ownership

P6.2 is complete as an isolated read-only candidate-retrieval prerequisite. It
does not classify weak versus strong similarity, persist or review a finding,
change Agent visibility, execute a semantic effect, run a model, schedule a
job, enable canonical traffic, or measure target-corpus precision. P6.3 is the
next local task. P6.7 owns shadow precision sampling; P7 owns durable worker
scheduling; P8 plus explicit approval owns activation; P2.8 remains separately
dependent on operator-supplied rehearsal inputs.
