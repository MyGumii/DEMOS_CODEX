# P1.6 personal/part space lifecycle evidence

Date: 2026-08-13 (Asia/Seoul)

## Result

P1.6 passes its isolated provisioning boundary. `SpaceRepository` is the one
canonical mapper and state owner for `knowledge_space`; organization and account
compatibility repositories delegate their space operations to it. The
framework-neutral `SpaceProvisioningService` reconciles the phase-1 lower bound
inside one `BEGIN IMMEDIATE` without registering a route or enabling traffic.

This evidence does not claim P1.7 scope/capability resolution, a live migration,
canonical traffic, lazy provisioning, higher-level spaces, personal writes, or
part writes.

## Frozen provisioning policy

- Every canonical user has one personal space, including a disabled user.
- Every active part has one part space even if it has no leader. A missing
  inactive-part space is skipped; an existing inactive-part space is retained.
- A new row is `active`, `write_enabled=0`, `generation=0`, `row_version=1`.
- Reconciliation never changes an existing space ID, status, write flag,
  generation, timestamps, or version. Valid pre-existing server IDs that do not
  use the current deterministic namespace remain authoritative and replayable.
- Team and responsibility spaces are never created. Existing future-space rows
  are counted for diagnostics, left untouched, and remain unavailable to phase
  1.
- Organization and account reads never lazy-create. A newly committed part is
  `not_created` until an explicit later reconciliation changes it to
  `write_disabled`.

## Transaction and idempotency boundary

- The administrator, current `scope_epoch`, all users, all active parts, and the
  final lower-bound report are checked in the same write transaction.
- The operation key is actor-scoped. Request correlation metadata is excluded
  from the semantic request hash, while actor, epoch, reason, operation type,
  and contract version are bound.
- Each newly inserted space commits with exactly one immutable provision audit
  and one `knowledge_space.provisioned` outbox event. A command audit and the
  terminal dedup result commit in the same transaction. A no-change command
  emits no domain outbox event.
- Exact replay returns the original semantic result with the caller's current
  request ID. Replay validates every stored owner/space pair against the current
  canonical row; created outcomes additionally require the deterministic
  server ID. Corrupt owner syntax, order, counts, identity, or operation binding
  fails closed as `IDEMPOTENCY_CONFLICT`.
- Scope-stale rejection is stored as `failed_final` with one rejection audit
  and no domain row/outbox. Domain, audit, outbox, and before-commit failpoints,
  plus injected repository failures, roll back space, audit, outbox, and dedup.
- Request metadata is allowlisted and rejects credential, CSRF, lease, token,
  cookie, password, and secret-shaped keys before persistence.

## Cross-process proof

Two fresh Python subprocesses share one P0.2-isolated WAL database containing
40 canonical users (including one disabled user) and four active parts:

1. The same actor and operation start from a barrier. One transaction creates
   44 spaces; both callers receive the same semantic result with their own
   request ID. The database contains one dedup row, 44 domain audit rows, one
   command audit, and 44 outbox rows.
2. Two distinct operations start from a barrier. One returns `created`, the
   other `no_change`; both commit stable terminal results. Space cardinality is
   still exactly 40 personal plus four part spaces, and no `SQLITE_BUSY`, lock,
   or uniqueness error escapes.

No process-local lock participates in either proof.

## Deliberate non-cutover boundary

- `SpaceProvisioningService` is not registered in `app_code`, `app_notion`, the
  optional Blueprint, or the P1.5 administrator adapter. The composition slot
  remains unbound.
- No live database is created or migrated. The schema-v2 fingerprint is
  unchanged because P1.6 uses existing tables, indexes, and triggers.
- No scope selector or capability is returned. Clients cannot submit a space ID
  to this service, and P1.7 owns all actor/space authorization.
- No projection, job worker, materializer, knowledge read/write, or publication
  path is started or redirected.
- `KNOWLEDGE_CORE_HIGHER_SPACES` and all traffic/write flags remain fail-closed.
