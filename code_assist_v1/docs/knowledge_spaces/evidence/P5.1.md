# P5.1 persistent fenced lease service evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P5.1 passes the tested persistent-lease implementation gate behind disabled
canonical traffic. The existing canonical `item_lease` row is now owned by a
transaction-scoped repository and service for acquire, heartbeat, owner
release, and authorized force release. Generations are monotonic, token
evidence is HMAC-only, stale and absolute expiry use SQLite time, scope is
revalidated at commit, and terminal mutations bind lease state, operation
result, audit, and outbox atomically.

This is not a feature rollout. No route or feature flag was registered or
enabled; no live database, source tree, worker, or production traffic was
accessed. The service receives its active/old HMAC keys from an external
protected provider; this task does not create a local secret file or enable a
deployment key provider. P2.8 remains separately blocked on operator-approved
rehearsal inputs.

## Frozen lease contract

- A raw lease token is strict unpadded base64url text of length 43 and decodes
  to exactly 32 bytes. Only
  `HMAC-SHA-256(key[hmac_key_id], "knowledge-lease-v1\\0" || item_id || 0x00 || raw_token)`
  is persisted.
- Acquire succeeds only for an active item with a free or expired canonical
  fence. It captures item row version/base revision and increments generation
  exactly once.
- Expiry reclaim and force release increment generation. Exact owner release
  clears the holder fields while preserving the current generation. A stale
  token or generation can never become current again.
- Heartbeat requires the exact actor, session, token HMAC, generation, and
  non-expired lease. It changes only heartbeat/stale expiry and never extends
  beyond the absolute expiry. It deliberately has no operation-dedup, audit,
  or outbox row.
- Acquire, owner release, and force release own one short managed transaction,
  revalidate current EDIT/FORCE_RELEASE authority, and commit operation replay,
  audit, and outbox with the lease mutation.
- Active and old verification keys permit an already-held lease to heartbeat
  or release after rotation. New acquisitions always use the active key.
- Edit-fence validation checks expected item row version, expected current
  revision, captured base, holder/session/token/generation, expiry, and current
  scope in the caller's P5.2 transaction. Failure preserves the local draft and
  offers only view-current, copy-draft, and reacquire-and-compare recovery;
  force overwrite is false.
- Raw tokens are excluded from command reprs and are not present in results,
  logs, SQLite rows, WAL bytes, audit/outbox/dedup JSON, or error details.

release needed to close them.

## Failure and concurrency proof

Acquire failpoints after generation calculation, after holder write, and
before commit leave the prior fence plus dedup/audit/outbox state unchanged.
Force-release failpoints after generation change and before commit retain the
original holder and generation. Reusing one operation ID with a different
token is an idempotency conflict, not a second mutation. A membership move,
scope-epoch change, or explicit revoke prevents later heartbeat or save-fence
validation.

The real process gate starts 40 separate `python -E` interpreters over one
isolated canonical SQLite database. The committed state contains exactly one
holder at generation 1. The other 39 callers receive the domain `LEASE_HELD`
outcome rather than a busy/locked transport failure.
