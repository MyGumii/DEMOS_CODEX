# P4.5 canonical publication route and shared modal evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P4.5 passes its disabled canonical-write implementation boundary. The exact
publication preview/status/cancel/commit and target-discovery API is available
as a dependency-injected route adapter, and knowledge upload, canonical chat
promotion, and both Notion publish entry points share one
personal/current-part/both modal with the permanent no-sync warning and
target-specific outcomes.

This evidence does **not** enable `KNOWLEDGE_CORE_PERSONAL_WRITES`, part reads or
writes, canonical traffic, a live route, a worker, or a production database. It
does not claim a completed `PUB-*` scenario. P4.6 owns exhaustive SQL failpoints,
real process/restart races, 1,000 exact retries, and the complete
`PUB-001..013` acceptance gate.

## Frozen server boundary

- `register_canonical_routes` optionally registers the complete four-route
  publication surface alongside P3.7 reads. `register_publication_routes`
  registers only `GET /spaces` plus those four routes for a Notion-only host;
  conversation, retrieval, management, summarization, and Agent execution
  dependencies cannot be reached through that registrar.
- Every route resolves actor user ID and scope epoch from the injected server
  principal. Browser JSON or multipart cannot supply or override authority.
- JSON rejects duplicates, extra members, non-finite/over-complex values, and
  oversized manual Markdown. Multipart accepts exactly one bounded upload and
  preserves its exact bytes, filename, media type, and optional title.
- Every mutation binds the body operation ID to `Idempotency-Key`. Commit binds
  the exact preview ID, source-snapshot SHA, and personal/part/both mode and
  returns only the contracted per-target fields.
- Automatic `OPTIONS /api/knowledge/v1/publication-previews` is the sole browser
  capability probe. It is non-mutating and does not call a publication service.
  The transport normalizes only 404 to absent; authorization, server, transport,
  or malformed-response errors remain errors.
- Composition can bind the standalone publication surface for the Notion host
  without canonical conversation services. The rollout parser still rejects
  personal writes, so the path is testable but not production-enabled.

## Frozen shared UI boundary

- `knowledge_publication.js` derives available modes only from the immutable
  ready preview and names the part from canonical target discovery. It disables
  unavailable part/both choices and displays the exact permanent independence
  warning for `both`.
- The modal freezes preview ID, source-snapshot SHA, allowed modes, and target
  list before commit. It never receives raw actor identity. Warnings and result
  text use DOM text nodes rather than source-controlled HTML.
- Queued/extracting previews poll the durable status endpoint. Queued and ready
  cancel actions call the durable cancellation API with a fresh operation ID;
  the modal is non-closeable until cancel or commit reaches a known result.
- Target outcomes are rendered independently as created, provenance added,
  changed-source update proposed, or no-op. A result action switches to the
  exact canonical space, reloads management state, highlights the exact item,
  and emits only validated IDs.
- Canonical chat promotion derives the stored conversation message range from
  the server conversation. Upload requires exactly one browser file. Notion
  saves a dirty main editor or side peek before preview creation.
- Notion uses a pure fail-closed bridge: only an authoritative absent probe may
  call the legacy preview. A probe exception or canonical preview/commit unknown
  outcome is surfaced and never followed by a legacy mutation. The existing
  legacy preview/approval flow remains intact when the canonical surface is
  absent.
- Notion target actions open the Code host with validated space/item UUIDs; the
  canonical browser consumes those IDs through the same exact target action.
