# P6.5 transactional merge evidence

Date: 2026-08-15 (Asia/Seoul)

## Result

P6.5 passes its isolated transactional-merge task behind disabled canonical
traffic. A current human curator must confirm one three-pane preview built from
two fixed current revisions and the exact result Markdown, then present two
valid item-specific edit leases/fences before one atomic merge may commit.

This is not the aggregate P6 gate. It adds no route or UI, runs no model,
enables no feature flag or traffic, and does not implement change-proposal
rebase/apply, review-queue UI, or shadow precision. P6.6-P6.8 retain those
responsibilities.

## Preview and authority boundary

- Preview requires an authenticated current `CURATE` capability in one
  concrete space and two different active items whose supplied revisions are
  still current. It reads no live legacy root and performs no write.
- The source/target revision rows and bodies, item row versions/statuses,
  complete affected semantic-edge rows, and complete affected item-relation
  rows form one canonical snapshot. Inline bodies are verified against their
  immutable byte hashes. Blob-backed bodies require an injected bounded loader;
  bytes are loaded outside SQLite and the entire authorized snapshot is then
  reread and compared before preview is returned.
- The three panes are exactly `merge_source`, `merge_target`, and `result`.
  The result revision ID is deterministic from the target plus the fixed
  snapshot and exact result evidence. The preview SHA-256 binds all pane IDs/
  hashes, item row versions/statuses, result size/hashes, edge/reference impact,
  and rule version.
- No process-memory preview cache is authoritative. Apply repeats the exact
  confirmed result Markdown and recomputes the fixed preview before opening its
  write transaction. Changed Markdown, revision, row version, edge, reference,
  lifecycle, or curation evidence makes the preview stale.
- Apply re-resolves current `CURATE` authority and validates both current
  `EDIT` lease proofs in lexicographically sorted item-ID order. Each proof is
  bound to its item, editor session, raw-token HMAC, fencing generation, base
  row version, and base revision. One valid lease cannot substitute for the
  other.

## Atomic effect, replay, and no-rewire boundary

- The service owns one short write transaction. The request hash binds both
  token HMAC/key identities, lease/session/fence tuples, fixed revisions,
  preview hash, result hashes/size, actor scope epoch, and operation ID. Raw
  tokens and authorization metadata never enter SQLite.
- Success queues one target `curation.rescan` job, inserts one immutable target
  `merge` revision/body and `revision_rescan` transition, moves the target
  current pointer to that result and its curation state to provisional, and
  marks the source `merged` with `redirect_item_id=target`.
- The same transaction writes one active immutable `merged_into` relation from
  the source fixed revision to the target result revision and one immutable
  `merge_event` bound to the operation, preview, original target revision, and
  relation. It obsoletes pending/approved fixed-revision findings and proposals,
  removes both FTS rows, increments the space generation once, releases both
  leases, and commits one audit/outbox event plus job/merge operation results.
- Semantic edges are never moved, recreated, retargeted, or type-changed. The
  repository captures every affected edge identity/endpoints/evidence revision,
  updates only lifecycle/revalidation metadata, and proves after the write that
  the semantic identity multiset is unchanged. Affected rows end inactive with
  `needs_revalidation=1`; later review must decide any replacement relation.
- A committed exact replay is resolved from immutable operation/result/
  relation/event closure before current-state preview checks, because the
  successful merge intentionally changes both items. It returns the stable
  result with the new request ID and performs no second mutation. Reusing the
  operation ID with changed content or any other request evidence fails as an
  idempotency conflict.
- Invalid second lease stores a stable terminal lock error without job or
  domain effects. Failpoints after dual fence validation, rescan enqueue,
  result revision, source state, redirect/event, dual release, audit, outbox,
  and immediately before commit prove rollback of both items and all related
  rows.
