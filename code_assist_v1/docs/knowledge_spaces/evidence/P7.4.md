# P7.4 backup and isolated restore evidence

Date: 2026-08-15 (Asia/Seoul)

## Result

P7.4 passes its P0.2-isolated, disabled-service/traffic implementation boundary.
SQLite online backup, a durable global GC hold, exact referenced-blob manifest,
atomic completed-directory publication, 96/30/12 UTC retention, and an isolated
restore with complete projection rebuild are implemented behind explicit
operator commands.

This is not the aggregate P7 or `G-12` production gate. P7.5 still owns the
Windows service account, ACL, scheduling, and off-machine destination; P7.6-P7.8
own target health/fault/load evidence; P7.9 owns the signed target-server restore
report. No production service, feature flag, traffic, worker, live root,
canonical live database, or external backup target was started or accessed.

## Online snapshot and durable hold

- `BackupRepository.begin()` creates exactly one preparing global GC hold. A
  second active run is rejected. `begin_copying()` atomically installs the exact
  snapshot-derived blob set; terminal verified/failed state releases the hold.
- SQLite's online backup API writes only to a pre-created, one-link,
  non-reparse, identity-bound destination. The standalone snapshot is placed in
  DELETE journal mode and checked for page facts, current schema/catalog/source
  ID, `quick_check=ok`, zero FK violations, and audit high-water.
- The self-hashed manifest binds application/build/configuration/key-set
  versions, current seven-version physical/catalog checksums, approved SQLite
  version/source ID, snapshot hash/size/high-water, and the sorted exact blob
  count/bytes/hash set.
- Staging is a pinned child of an eligible backup root. Production rejects a
  source-overlapping or same-volume target. P0.2 tests alone may use the same
  isolated volume. Only a verified staging tree is exposed by a same-volume
  atomic directory rename.

## Crash, concurrency, and GC proof

- Real spawned processes crash with `os._exit(73)` at each frozen boundary:
  `backup.after_hold_acquire`, `backup.after_database_snapshot`,
  `backup.after_blob_manifest`, and `backup.before_finalize_rename`.
  No boundary records false success; the same run resumes to byte-identical
  completed storage and a verified ledger.
- A separate writer process commits forty users while the online snapshot runs.
  The backup is one integral database state and the live database reaches all
  forty commits.
- Preparing/copying globally block GC, the exact copying blob set remains held,
  and a GC claim blocks a new backup. Catchable failures store only canonical,
  sanitized error codes and leave no active hold.

## Retention and deletion proof

- Selection is deterministic and independent of input order: keep the latest 96
  runs, the newest restore point for the latest 30 UTC days, and the newest for
  the latest 12 UTC months. Active, failed, missing, or unverified storage is
  never selected for deletion.
- Before deletion, durable verified state, manifest, snapshot, every blob, and
  the exact tree are checked again. The directory is atomically renamed to a
  `.pruning-...partial` quarantine name before files are handle-deleted. A
  failure cannot leave a partial tree discoverable as a completed backup.
- Historical immutable `backup_run` evidence remains in SQLite; retained
  availability is the presence of its re-verified completed directory.

## Isolated restore and projection rebuild

- Restore requires a distinct empty canonical layout. Data, database parent,
  blob, and projection directories are identity-bound and delete-pinned for the
  whole copy, WAL activation, database verification, and projection rebuild.
  A real rename attempt during projection rebuild is denied.
- The manifest/snapshot is fully verified before target creation. Snapshot and
  blobs are streamed through pinned one-link handles. The restored database
  enters WAL mode and the captured preparing hold is terminally closed with the
  stable `RESTORED_BACKUP_HOLD_CLOSED` code.
- Pre-rebuild canonical integrity permits only stale search projection. Full
  materialization then rebuilds every space, followed by complete quick/FK/
  schema/postcondition verification and zero active holds.
- The isolated proof meets RPO at most 60 minutes and RTO at most 240 minutes,
  with `integrity_mismatch_count=0`. Manifest or snapshot tamper is rejected
  before any target database/blob/projection write.

## Operator boundary and recovery decision

- `tools/backup_restore.py` exposes explicit `create`, `prune`, and
  `restore-drill` commands. `ops/backup.ps1`, `ops/backup-retention.ps1`, and
  `ops/restore-drill.ps1` invoke the official venv with explicit storage paths;
  all three wrappers parse successfully. Import starts nothing.
- ADR-016 records phase 1 as roll-forward-only after the first canonical
  production write. P8.1 must copy the decision and this evidence hash into the
  signed approval packet. There is no unimplemented delta-export promise hidden
  behind a rollback label.

## Safety and deliberate limits

- No application route exposes these operations. The explicit CLI is an
  operator boundary, not an HTTP endpoint or background scheduler.
- P7.4 does not configure the production service account, NTFS ACL, Task
  Scheduler/Windows service, backup monitoring, or real off-machine target.
- The isolated test's successful RPO/RTO is implementation evidence, not the
  signed target-server P7.9 drill or proof of real backup age.
- Retention deletion preserves the immutable database run ledger. A crash after
  quarantine rename can leave a `.pruning-...partial` directory for operator
  review; it is never treated as a completed restore point.
- No personal or part write flag, migration, worker, model, projector service,
  WSGI host, or production traffic was enabled.
