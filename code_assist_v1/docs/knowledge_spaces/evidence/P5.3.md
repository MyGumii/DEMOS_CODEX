# P5.3 deactivation and restore evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P5.3 passes the tested deactivation/restore implementation gate behind
disabled canonical traffic. Separate service-owned transactions revalidate
current scope and expected item version, preserve item/revision/graph identity,
record immutable lifecycle episodes, maintain transactional search visibility,
and commit one exact audit/outbox pair per successful operation.

This is not a feature rollout. No lifecycle route or UI was registered, no
feature flag was enabled, no live database/blob root/source tree was opened,
no worker or web process was started, and no personal/part write traffic was
authorized. P2.8 remains separately blocked on operator-approved rehearsal
inputs.

## Frozen lifecycle contract

- `DeactivateItemCommand` requires an authenticated principal and captured
  scope epoch, exact space/item IDs, positive expected item row version,
  caller UUID operation/request IDs, and a trimmed 1..2,000-character reason.
- The service re-resolves `DEACTIVATE` capability and SQLite time inside one
  `BEGIN IMMEDIATE` transaction. The request hash binds actor/epoch,
  space/item/version, operation type, and normalized reason.
- A foreign unexpired lease returns stable `LEASE_HELD` and is not released.
  An actor-owned or expired lease is cleared with a persistent fence increment
  before the item can become inactive, making every prior token stale.
- Deactivation inserts the next immutable episode and sets purge eligibility
  exactly 7,776,000,000 ms after database deactivation time. It CASes the item
  active→inactive, preserves current revision/curation state, removes one
  published search row or none for a non-published item, advances space
  generation, and writes one reasoned audit plus one outbox event.
- `RestoreItemCommand` requires current `RESTORE` capability, operation ID, and
  expected inactive item row version. It closes only the latest open episode,
  CASes the same item inactive→active, preserves current revision/curation and
  every edge/reference row, conditionally restores published search content,
  advances space generation, and writes one audit/outbox.
- Inline Markdown is verified directly. Blob-backed content is loaded through
  an injected protected loader outside the write transaction, checked for
  strict UTF-8/size/SHA-256, and rebound to the item/revision/body inside the
  transaction. No production loader or route is registered by P5.3.
- The frozen P5.3 policy returns `review_job_queued=false` and creates no
  durable review job. Later curation/worker phases may introduce a separately
  versioned review policy; a replay cannot reinterpret the stored result.
- Exact operation replay returns the stored response with the new request ID,
  adds no episode/audit/outbox/search/generation effect, and for blob-backed
  restore requires no second load. Changed intent or stale state fails closed.
- Neither command inserts, updates, or deletes `knowledge_revision`,
  `knowledge_revision_body`, `knowledge_edge`, or `item_relation` rows.

tests in this task exercise transaction contention in one Python process;
P5.7 still owns actual two-web-process lifecycle races, 40-client load, and the
aggregate `REV`/`LEASE`/`LIFE` P5 gate.

## Atomicity and failure proof

Named deactivation boundaries are:

```text
lifecycle.after_lease_clear
lifecycle.after_episode
lifecycle.after_item_state
lifecycle.after_search_visibility
lifecycle.after_audit
lifecycle.after_outbox
lifecycle.before_commit
```

Named restore boundaries are:

```text
lifecycle.after_episode
lifecycle.after_item_state
lifecycle.after_search_visibility
lifecycle.after_audit
lifecycle.after_outbox
lifecycle.before_commit
```

Every named boundary restores the exact prior item, lease, episode, revision,
edge, reference, search, generation, audit, outbox, dedup, and durable-job
state. A dynamic matrix independently observes every application DML statement
and raises after each of 9 deactivate and 8 restore writes. The sequence count
is frozen; each injected failure restores the exact baseline and passes all
canonical migration postconditions.

Two `ItemLifecycleService` instances racing distinct operations against one
database produce one success and one stable `STATE_CONFLICT` for deactivate and
for restore, with one state transition/audit/outbox. This is a bounded
same-process proof, not the P5.7 cross-process/load claim.

## Gate and residual ownership

P5.3 is closed as a tested implementation prerequisite behind disabled
traffic. It does not enable lifecycle endpoints/UI, live flags, databases,
blob providers, workers, or writes. P5.4 owns activity/version UI, P5.5 owns
lease-editor UI, P5.6 owns administrator purge and `LIFE-007..010`, and P5.7
owns actual web-process lifecycle contention, 40-client load, and aggregate P5
acceptance. P6/P7 still own curation/review execution, projections, workers,
backup/recovery, and operations; P8 plus explicit operator approval owns
production activation.
