# P1.5 organization service and administrator API evidence

Date: 2026-08-13 (Asia/Seoul)

## Result

P1.5 passes its isolated implementation boundary. The canonical organization
repository/service implements stable hierarchy changes, membership and leader
CAS, impact-bound previews, exact inactivation resolution, scope invalidation,
and atomic audit/outbox/dedup. An explicit dependency-injected Flask adapter
implements the nine contracted administrator operations. `ORG-001..006` and
actual two-process contention have permanent execution proof.

This evidence does not authorize a live migration, default route registration,
space provisioning, canonical knowledge traffic, workers, projections, or
personal/part writes.

## Organization transaction boundary

- The fixed `AMHS담당` root owns stable team and part IDs. Rename and move never
  recreate a unit. Parent-kind, cycle, active-sibling name, and immutable-root
  constraints are rechecked in the write transaction.
- Each active user has at most one current part membership; intentionally
  unassigned remains valid. Membership assignment/move/unassignment compares
  the user row version, current leader episode, and part aggregate fence when
  required, increments `scope_epoch`, fences old-part leases, and invalidates
  exact old-epoch jobs.
- Every leader episode compares the current nullable assignment ID and part
  `row_version`; opening, replacing, or closing leadership advances the part
  aggregate. A write-enabled part cannot be left leaderless.
- A move uses a five-minute DB-time HMAC preview and explicitly retains
  membership, leader, and owned-space identities. Permanent coverage moves a
  populated part and proves its membership ID, leader-assignment ID, space ID,
  user row, and scope epoch remain unchanged.
- Inactivation refuses active direct children, binds the complete impact hash,
  requires each current member exactly once with its user-version/destination,
  closes the exact leader episode, and freezes an existing owned space rather
  than deleting it. Missing spaces remain `not_created`; disabled future team
  spaces are also detected and frozen instead of being silently orphaned.
- Service DTO boundaries independently reject Boolean-as-integer CAS values.
  Repository validation and schema triggers remain a second line of defense.
- Successful mutations, immutable audit, outbox, and terminal actor-scoped
  dedup commit together. Stable pre-write rejection commits `failed_final` and
  replays the exact error; post-write/transient failures roll back the entire
  envelope. Failpoints cover domain, audit, outbox, and before-commit stages.

## Administrator HTTP boundary

- Exactly nine routes are available through `register_admin_routes`; purge is
  absent. Import, default composition, `app_code`, and `app_notion` expose zero
  administrator routes.
- The adapter accepts only a canonical server-resolved admin principal with the
  current scope epoch. Client actor fields are forbidden. Actual auth hooks
  enforce Host, Origin, session CSRF, and mandatory-password policy before the
  adapter.
- Body `operation_id` is mandatory. A present `Idempotency-Key`, including an
  empty value, must be a canonical UUID identical to the body value.
- Request bodies are limited to 64 KiB and reject malformed UTF-8, duplicate
  keys, non-finite numbers, excess depth/nodes, unknown fields, noncanonical
  user/UUID values, Boolean/oversized versions, and blank required text.
- Known errors and unexpected failures use a correlated, no-store stable JSON
  envelope. Unexpected exceptions expose only `INTERNAL_ERROR`, never raw
  exception text.
- Registration fails before any canonical route is attached if the Flask host
  or Blueprint can shadow a semantic path, implicit HEAD/OPTIONS method, final
  namespaced endpoint, URL prefix/default/subdomain, repeated named attach, or
  Blueprint-local callback/view/nested/static surface.

## Cross-process proof

Two fresh Python processes share one P0.2-isolated WAL database and start from
an explicit barrier:

1. The same actor and semantic `operation_id` create one team. Both callers
   receive the same resource, their current request IDs are preserved, and the
   database contains one committed dedup row, one audit row, and one outbox row.
2. Two different operations assign the same user/version to different parts.
   Exactly one commits, the other becomes a stable `REVISION_CONFLICT`; one
   current membership remains, `scope_epoch` and user row version advance once,
   and each terminal operation has one audit/outbox record.

No process-local lock participates in either proof.

## Deliberate non-cutover boundary

- No schema migration was added or executed against live state. P1.5 uses the
  already-reviewed schema-v2 catalog only in isolated fixture databases.
- New part creation intentionally returns `space_status=not_created`; P1.6 is
  the sole owner of personal/part-space provisioning.
- Team/responsibility spaces remain future-only, hidden, and write-disabled.
  Their optional rows are considered during organization impact/inactivation
  solely to prevent orphaned active state.
- The nine-route adapter is injectable for tests but remains unregistered from
  production hosts and default composition. Canonical account/organization
  traffic is not cut over.
- No knowledge, publication, edit, lifecycle, retrieval, worker, materializer,
  or part-write flag was enabled.
