# P3.1 canonical conversation and immutable-scope evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P3.1 passes its inert canonical conversation boundary. New conversation and
message ownership lives in the central database, each conversation retains one
immutable personal or part space, and every read, mutation, reconnect, and
committed replay revalidates the active account and current space facts.

This evidence closes the P3.1 implementation task and the focused
`CONV-011`/`CONV-012` behavior. It does **not** register HTTP/SSE routes, switch
legacy traffic, enable personal or part knowledge reads/writes, claim all of
`CONV-013`, or claim the P3/G-07 gate. P3.2 owns pins and explicit context
bindings; P3.3-P3.6 own retrieval, Agent streaming, compatibility UI/API, and
cutover.

## Frozen behavior

- Create, load, cursor-list, rename, and archive use canonical conversation
  rows. Space identity and captured scope epoch cannot be changed.
- A retry or reconnect for one conversation-turn operation creates exactly one
  user message and at most one final assistant message. Ordered immutable turn
  events provide a reconnect cursor.
- Completed, failed, and cancelled terminal outcomes are exact-once. A failed
  turn stores only `{code,retryable,schema_version}`; raw exception text and
  secret-bearing error payloads are not accepted. A cancelled turn stores no
  error or assistant response.
- The terminal turn row, terminal event, operation result, audit event, and
  outbox event commit in one service-owned transaction. An injected audit
  failure rolls the whole terminal transition back to the reconnectable
  accepted checkpoint.
- Compact summaries bind one fixed existing message prefix. Replacing a summary
  invalidates the prior active row while preserving immutable history, and an
  injected audit failure preserves the old active summary.
- Every committed create/update/turn/summary replay rechecks current access.
  Freezing a part or making membership scope stale blocks replay rather than
  returning stored part data.
- `LegacyJsonSessionAdapter` reads canonical rows only. It performs no legacy
  filesystem read/write or parallel fallback, and a P2.5 session identifier is
  resolved only through its stored SHA-256 migration evidence.

and SSE route/reconnect composition, P3.5 owns diagnostics/canaries, and P3.6

legacy Flask chat/session routes remain authoritative and all Knowledge Core
