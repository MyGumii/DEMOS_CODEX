# P7.6 production health and metrics evidence

Date: 2026-08-15 (Asia/Seoul)

## Result

P7.6 passes its P0.2-isolated, disabled-service/traffic implementation
boundary. Both production web applications receive one versioned, read-only,
secret-free readiness provider, and the Windows startup wrapper requires its
exact ready contract before starting worker/projector roles.

This is not target deployment, monitoring, aggregate P7, or final `G-10` /
`G-11` / `G-12` evidence. No SCM service, account, ACL, production listener,
worker, monitoring sink, live root/database, feature flag, model, or traffic
was accessed, started, installed, or changed. P7.7-P7.9 retain randomized
fault/restart, target-class load, and signed target restore/service authority.

## Versioned secret-free boundary

- The report schema is `code-assist.production-health`, version 1. Both
  `app_code` and `app_notion` preserve its HTTP 200/503 status and send
  `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`.
- `ProductionHealthService` single-flights and deep-copy caches observations
  for five seconds. Any exception is reduced to stable
  `health_observation_failed`; exception text never crosses the route.
- The report contains no paths, record IDs, owner claims, account names,
  request/payload bodies, stored error JSON, tokens, passwords, or arbitrary
  environment values. The development fallback also omits token source/path.
- Build evidence binds the application version, canonical config SHA-256,
  migration catalog checksum, and exact current migration row. It does not
  claim an installed target build or target monitoring pipeline.

## Read-only storage and SQLite proof

- Before any database/file/disk observation, the database file, its parent,
  and the blob root are re-probed. Each must exist on fixed local NTFS, contain
  no reparse component, and resolve to the configured path. A failure returns a
  minimal 503 with role eligibility booleans and performs no SQLite, file-size,
  or free-space observation.
- SQLite connections retain the canonical path/file-identity checks and run in
  read-only/query-only mode. Persisted metrics are collected in one deferred
  read snapshot. A permanent test hashes the DB, WAL, and blob tree before and
  after collection and proves no change.
- Readiness binds exact SQLite version/source ID, compile options including
  `ENABLE_FTS5`, executable FTS5, required pragmas, schema version, quick check,
  and foreign-key violation count. The isolated workstation runtime override
  is allowed only when `CODE_ASSIST_TEST_MODE=1`; production service composition
  never enables it.

## Operational metrics and no-go rules

- Process database counters expose execute, SQLite busy, SQLite locked, and an
  honest application retry count. No Python DB retry policy exists, so that
  last counter remains zero; durable retry counts come from canonical queues.
- Job and outbox aggregates include exact state counts, attempts, retries,
  oldest nonterminal age, dead outbox, and failed/dead job counts. Stored error
  bodies are deliberately excluded.
- Lease metrics expose active/stale/released counts. Projection metrics expose
  desired/built generation, total/max lag, lagging/error counts, and oldest lag
  age. Backup readiness requires a verified backup no older than 45 minutes.
- Storage reports DB/WAL bytes, referenced blob count/bytes/verification, and
  free bytes on DB and blob volumes. Each volume must have at least three times
  DB plus referenced-blob bytes available.
- Invalid flags, configured failpoints, unapproved runtime/schema, unsafe
  storage, missing/stale backup, dead outbox, failed/dead jobs, projection
  errors, unverified referenced blobs, or low capacity produce sorted stable
  reason codes and HTTP 503.
- `start-services.ps1` requires the exact schema/version, `ready` status, and
  zero reason codes for both web hosts before starting worker/projector.

## Safety and deliberate limits

- Positive readiness tests use only isolated `D:\CodexTestTemp` databases and
  the explicit test-only SQLite runtime override. Production code requires the
  exact approved SQLite build and never enables the override.
- Tests compose Flask/Waitress only through existing isolated random-loopback
  process fixtures. They do not invoke WinSW/SCM or the installation/start
  wrapper and do not inspect live-looking compatibility roots.
- The five-second integrity/metric cache bounds request cost; P7.8 must measure
  target-server latency and resource impact. P7.7 must still prove restart and
  fault convergence, and P7.9 must still produce signed target restore results.
- No password, token, raw body, stored exception/error payload, filesystem path,
  owner claim, or record identifier is present in the health response or this
  evidence.
