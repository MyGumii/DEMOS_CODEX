## SQL failure and process proof

The SQL matrix patches only the managed test connection after fixture creation.
It discovers the successful path's application DML sequence, excluding the
connection's private temporary FTS runtime probe. It first aborts after the
terminal operation-dedup write to prove the full sequence can be rolled back,
then repeats the same operation and raises immediately after each DML write in
turn. The sequence itself is compared on every iteration, so a missing,
reordered, or newly introduced write requires explicit review.

```text
dual_create_sql_write_boundaries=24
dual_update_proposal_sql_write_boundaries=16
2 passed in 8.12 s
```

After every injected failure, the test compares publication operation/target,
lineage, item/revision/body/source, finding/proposal, audit/outbox, operation
dedup, preview status/version/completion, and space generation state with the
pre-operation snapshot, then runs all canonical schema postconditions. The
final non-injected attempt succeeds.

The process matrix starts independent `python -E` interpreters against the
same isolated canonical SQLite database:

- four simultaneous exact operation retries return one byte-equivalent stored
  result with no busy/locked error;
- a worker commits and exits with code 23 before emitting a response, after
  which a new process returns the exact durable result;
- two distinct previews/operations with equal content race and converge to one
  `created` pair followed by one `provenance_added` pair, with two items and two
  revisions total;
- independent processes reconstruct a ready preview, poll it, durably cancel
  it, and repoll the cancelled state with zero knowledge rows.
