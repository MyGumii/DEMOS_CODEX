# P1.9 minimal durable-work kernel evidence

Date: 2026-08-13 (Asia/Seoul)

## Result

P1.9 passes its P0.2-isolated minimal durable-work boundary. The implementation
supplies durable enqueue, exact replay/conflict, claim/start/renew/progress,
expiry/retry/dead, cancellation, stable result, and one-transaction canonical
effect primitives. It also supplies an immutable exact-version handler
registry and immediately pre-commit authorization/expected-state validation.

This evidence does not claim an operating daemon, publication handler,
producer cutover, cross-job GPU scheduling, projection materializer,
production service, live migration, or enabled canonical traffic/write flag.

## Repository and registry contract

- `JobRepository` accepts mutations only within an existing caller-owned
  transaction. The worker kernel opens default IMMEDIATE transactions; direct
  producers own the enqueue transaction together with operation dedup, audit,
  outbox, and their command result.
- Input, expected-state, authorization, capability, result, and error payloads
  use a strict RFC 8785/I-JSON subset. Object keys are recursively ordered by
  UTF-16 code units; floats, surrogates, non-string keys, and integers outside
  the exact interoperable range fail closed. Stored JSON and hashes are
  recanonicalized by the integrity scan before startup/claim.
- A new user job must match an `in_progress` operation-dedup reservation and
  its exact request hash. `committed` and `failed_final` operations cannot
  create new work. An already-created exact job remains replayable after its
  producer operation becomes terminal; a changed job/effect/input conflicts.
- The process registry is immutable and keyed by exact
  `(job_type, handler_version)`; each registered handler also freezes one actor
  kind, which startup and execution compare with the job row. Startup and claim
  fail closed on missing handlers, actor-contract drift, corrupted JSON/hash
  state, or an uncovered nonterminal version.
- Claim owner, attempt count, live expiry, state, and cancellation flag are
  repeated in every worker compare-and-swap. Attempt count is the ABA fence.
  Exhaustion uses the schema-legal two-step `running/claimed -> retry -> dead`.
- Queued/retry cancellation is immediate. Claimed/running cancellation is
  cooperative, and an expired cancel-requested claim converges to `cancelled`
  rather than becoming stranded or claimable again.

## Atomic effect boundary

- Handler preparation runs outside SQLite transactions. A later P7 heartbeat
  loop may renew long preparation, but an expired fence cannot commit.
- Immediately before a canonical effect, one IMMEDIATE transaction verifies
  the running claim, exact registered handler, current `ScopeResolver`
  authorization, captured scope epoch/current part/capability, and the
  handler-specific expected aggregate state.
- The handler applies its canonical SQLite effect and writes the stable
  `succeeded` result in that same transaction. Any callback, authorization,
  expected-state, cancellation, or fence failure rolls the effect back.
- After that rollback, a stable authorization/expected-state/permanent failure
  is recorded in a fresh transaction. Response loss after a successful commit
  returns the exact prior result and does not call the effect again.
- This exactly-once proof applies only to a canonical SQLite effect in the same
  transaction. File, network, model, and other nontransactional external
  effects are outside P1.9 authority.

## Process, restart, and authorization proof

The integration suite starts real fresh Python processes and uses explicit
barriers or hard exits. It proves:

- `JOB-001`: an enqueue committed immediately before process death remains
  queued and claimable;
- `JOB-002`: an expired running claim is recovered and a stale attempt fence
  cannot mutate the reclaimed job;
- `JOB-003`/`JOB-004`: process death after atomic domain-effect/result commit
  leaves exactly one effect and exact replay returns the stored result;
- `JOB-005` substrate: two processes competing for the same durable-job row
  produce at most one claim winner;
- `JOB-006`: account disable between preparation and commit produces zero
  canonical effect and one stable authorization failure;
- an expired cooperative cancellation converges to terminal `cancelled`.

A separate permanent unit acceptance covers the other `JOB-006` branch:
membership A→B and scope-epoch advancement after preparation reject the old
part effect, audit, and outbox while preserving the target row.

The `JOB-005` statement above is deliberately narrow. Different conflicting
GPU jobs, model ownership, fairness, and central serialization remain
P7.2/P7.7 work and are not claimed by this gate.

## Deliberate P4/P7 boundary

- No worker daemon, polling loop, heartbeat scheduler, operational backoff,
  actual publication/curation handler, job HTTP route, or service registration
  was added.
- No legacy producer was cut over. P4 uses this kernel for publication preview;
  P7 completes producer cutover, recovery operations, central GPU scheduling,
  monitoring, production WSGI/service packaging, and randomized fault tests.
- No projection exactly-once or external file/network effect claim is made.
- The current SQLite 3.50.4 binding remains development-only. This gate does
  not satisfy the approved production SQLite/source-ID requirement.
