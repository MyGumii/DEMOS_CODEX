# P1.4 user, audit, compatibility, and browser-security evidence

Date: 2026-08-12 (Asia/Seoul)

## Result

P1.4 passes its isolated implementation boundary. Canonical user, audit,
operation-dedup, outbox, and account-lifecycle behavior is executable against
P0.2-controlled temporary databases, and `AUTH-001..004` has permanent unit
and actual-Flask integration coverage. This evidence does not authorize a live
migration, broad canonical traffic, a worker, projection processing, or
personal/part writes.

## Canonical account boundary

- `UserRepository` imports legacy identifiers, hashes, roles, account status,
  display metadata, and mandatory-password-change state idempotently. Password
  hashes are excluded from DTO representations and session principals.
- Disable/re-enable is revision-CAS protected. Disable increments
  `scope_epoch`, clears the current part, closes current membership and leader
  authority under leader/write rules, revokes lease fences, invalidates all
  old-epoch jobs, and requests cancellation only for cancellable jobs.
  Re-enable does not restore the old part, lease authority, or job authority.
- Each account command binds `operation_id` to a semantic request hash.
  Successful commands commit domain changes, immutable audit, outbox, and the
  terminal dedup result in one transaction. Stable rejected commands commit a
  `failed_final` result plus rejection audit/outbox and replay the exact stable
  error; a different payload conflicts. Transient failures roll back fully.
- Leader replacement uses an actor-bound stable ID. A leaderless part cannot
  remain write-enabled, and a full 2,000-character command reason is preserved
  in audit while the role-assignment reason remains within its 1,000-character
  physical limit.
- User hard deletion is forbidden at repository, compatibility-adapter,
  legacy helper, and legacy HTTP endpoint boundaries. Shared knowledge,
  credentials, membership history, and audit references remain intact.

## Authentication and browser boundary

- The compatibility adapter imports legacy password-policy state, including
  the legacy default-password mandatory-change rule, and offers one cohesive
  authenticate-and-login operation with a redacted principal, exact
  `scope_epoch`, permanent session, and 256-bit session CSRF token.
- Both Flask hosts share one atomically published secret on concurrent first
  start. Existing malformed secret material fails closed.
- Every request Host must resolve to the explicit allowlist. Login/register
  require an exact same-origin Origin. Cookie-authenticated unsafe requests and
  explicit SSE initiation additionally require the exact session CSRF header.
  Auth responses are non-cacheable, and password change rotates the token.
- Production registration validates exact cookie name `session`, host-only
  domain, Path `/`, Secure, HttpOnly, SameSite=Lax, sufficiently strong secret,
  bounded lifetime, and HTTPS origins.
- Only the exact anonymous public-form POST shape bypasses cookie proof. Public
  duplicate uses `/auth/me` token bootstrap and a same-origin header POST.
- The browser helpers attach CSRF only to same-origin unsafe requests. Absolute,
  protocol-relative, backslash network-path, non-HTTP, and other cross-origin
  targets never receive the token.
- An existing corrupt/unreadable legacy registry returns 503 and cannot become
  an empty-registry first-admin bootstrap. A signed cookie for a missing account
  cannot authenticate.

## Deliberate non-cutover boundary

- Canonical DB account traffic remains disabled and no canonical feature flag
  was enabled. The current Flask login/profile/password/register compatibility
  traffic still uses `users.json` until the migration/cutover phase.
- Because legacy JSON read-modify-write is not a safe two-process canonical
  store, legacy account-status mutation is now rejected with
  `CANONICAL_ACCOUNT_LIFECYCLE_REQUIRED`; hard deletion is rejected separately.
  P1.5 must route versioned administrator lifecycle operations through the
  canonical service before operational disable/re-enable is claimed.
- Scope resolution, organization administration, personal/part-space
  lifecycle, knowledge traffic, workers, projections, and part writes remain
  outside P1.4 and disabled.
