# P1.7 scope and capability resolution evidence

Date: 2026-08-13 (Asia/Seoul)

## Result

P1.7 passes its isolated scope-resolution boundary. The framework-neutral
`ScopeResolver` resolves one authenticated actor against one canonical
transaction snapshot and exposes only the actor's personal space and current-
part space. It performs no domain mutation, provisioning, route registration,
configuration read, or feature transition.

This evidence does not claim `SPACE-006` end-to-end corpus isolation, a live
migration, canonical route cutover, enabled traffic, conversation binding,
publication, leases, personal writes, part writes, or the full P1 gate.

## Frozen resolver boundary

- The only trusted principal fields are canonical `user_id` and captured
  `scope_epoch`. Client role, part, leader, capability, and actor overrides are
  not accepted.
- A caller supplies an immutable `FeatureFlags` value and an already-active
  `ManagedConnection` transaction. The resolver never opens, commits, or rolls
  back that transaction and never reads flags from an environment or config.
- Active account status, current epoch, open membership, current part and its
  active team/responsibility ancestors, active part leader, and concrete space
  are reread from the same database snapshot.
- Normal Agent scope is personal/current-part only. Foreign, former-part,
  higher-level, frozen, inactive, missing, and forged targets share a
  deliberately undisclosed `NOT_FOUND` response. An administrator cannot use
  global role to widen normal Agent retrieval scope.
- An active canonical user without a personal space is an integrity failure.
  A current part without an explicitly provisioned part space is omitted and
  remains unavailable; selection never creates or repairs a row.
- Entitled and rollout-effective capabilities are reported separately. An
  active write-disabled row has read entitlement only. Publish, edit,
  deactivate, restore, and curate require both row-level write enablement and
  the matching rollout flag. Only a current-part leader or same-part system
  administrator is entitled to `force_release`; ordinary members are not.
- The default rollout snapshot is all-off. It yields no selectable space and
  denies direct resolution until a reviewed host supplies explicit read flags.

## Cross-process proof

Two fresh Python subprocesses share one P0.2-isolated WAL database and use
explicit start/commit barriers. One process atomically moves an ordinary member
from part A to part B while the resolver process starts from the old session
epoch and then uses the committed new epoch.

The proof establishes all of the following:

1. The old principal receives `SCOPE_STALE` after the move.
2. The new principal lists exactly personal plus part B.
3. Part A, a foreign part, a forged ID, a missing space, and schema-supported
   team/responsibility spaces all return the same concealed `NOT_FOUND` result.
4. An unassigned administrator cannot select another user's or part's normal
   Agent space.
5. A forged-on rollout snapshot cannot grant writes while canonical
   `write_enabled=0`.
6. Missing part-space and personal-space cases do not lazy-create rows; the
   latter fails as an integrity error.
7. Knowledge-space, audit, and outbox counts are unchanged by every resolver
   read.

## Deliberate non-cutover boundary

- `ScopeResolver` is not registered in `app_code`, `app_notion`, the optional
  Blueprint, or the P1.5 administrator adapter. Default composition remains
  inert.
- No live database is created or migrated. No schema object or reviewed
  fingerprint changes in P1.7.
- No environment/config flag is read or changed. All live traffic, projection,
  worker, higher-space, personal-write, and part-write flags remain off.
- No knowledge read/write route, conversation, publication, lease, search,
  graph, pin, or projection path is redirected in this slice.
