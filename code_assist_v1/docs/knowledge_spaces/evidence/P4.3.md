# P4.3 idempotent single/dual publication evidence

Date: 2026-08-14 (Asia/Seoul)

## Result

P4.3 passes its disabled implementation boundary. One exact ready P4.2 preview
can now be committed to the actor's personal space, current-part space, or both
through one service-owned immediate transaction. The operation produces a
stable per-target result and cannot partially publish a dual target.

This evidence does **not** register a publication route, enable a feature flag,
start a worker, touch a live database, enable part traffic, create a changed-
source proposal, or claim a completed `PUB-*` scenario. P4.4 owns the concrete
stable-source update finding/proposal and existing Notion-route consolidation;
P4.5 owns API/UI activation; P4.6 owns exhaustive SQL failpoints, process races,
1,000 retries, and the complete `PUB-001..013` acceptance gate.

## Frozen command and authorization contract

- `PublishPreviewCommand` requires a request ID, actor-scoped operation ID,
  server-authenticated actor ID, captured scope epoch, preview ID, exact
  `source_snapshot_sha256`, and `personal|part|both` target mode. Request
  metadata is reduced to the existing safe allowlist before audit persistence.
- A new operation rereads the active canonical actor and epoch, requires the
  preview to be ready/unexpired and owned by that actor, compares the caller's
  snapshot SHA with the frozen preview, and resolves only currently effective
  publish capabilities. Part or both additionally requires the preview's
  captured part to equal the actor's current canonical part.
- Operation dedup is reserved before domain work in the same transaction. An
  exact committed retry, including a retry carrying a new correlation request
  ID, returns the first stored result after independently checking the
  publication operation, target rows, canonical response JSON, and consumed
  preview binding. A reused operation with a different preview, snapshot, or
  target mode fails closed.

## Frozen target and provenance contract

- Each successful target response has the common nullable API shape:
  `space_id`, `outcome`, `source_artifact_id`, `item_id`,
  `resolved_revision_id`, `created_revision_id`, and `finding_id`.
- The exact same artifact/extraction or the same stable origin revision and
  body resolves `no_op`. A different origin with one unambiguous exact current
  body in the same space inserts one `item_source(role='evidence')` and resolves
  `provenance_added`. Multiple exact candidates or conflicting stable evidence
  fail closed.
- A new target creates an active/provisional item, immutable revision number 1
  with `change_kind='initial'`, exact inline/blob body, and
  `item_source(role='initial')`. It increments only that target space's
  generation and emits the provisional visibility event. Publication invokes
  no semantic relation or model/LLM path.
- A stable origin whose frozen revision/hash changed is not duplicated or
  overwritten. P4.3 returns the stable P4.4-required failure and rolls back;
  P4.4 will create the fixed source/base/target update finding/proposal.

## Frozen dual-target transaction contract

- `both` derives separate deterministic personal and part item, revision, and
  source IDs. It inserts one immutable lineage group whose source artifact,
  extraction, and normalized content hash match the preview and whose
  `sync_policy` is permanently `none`.
- The resolved personal item is the lineage origin. The part member derives
  from that exact personal item/revision. A pre-existing exact personal target
  may receive provenance while the part target is created; no synchronization
  pointer or automatic update exists.
- Publication operation/targets, lineage, item/revision/source effects, preview
  `ready -> consumed`, per-target audit, created-item visibility outbox,
  operation-level outbox, target generation, and committed dedup result share
  the transaction. An injected late outbox failure leaves all target, lineage,
  item, dedup, and preview state unchanged.
